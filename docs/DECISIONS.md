# 설계 결정 기록 (ADR)

결정 자체보다 **왜 그렇게 정했고 무엇을 포기했는지**를 남긴다. 나중에 뒤집을 때 근거를 다시 만들지 않기 위해서다.

---

## ADR-001. Next.js 풀스택 (TypeScript)

**결정**: Next.js(App Router) 하나로 UI·API·스케줄러를 모두 담는다.

**근거**
- 저사양 홈서버에서 **프로세스 수를 늘리지 않는 것**이 가장 효과적인 리소스 절약이다.
- 달력 UI는 클라이언트 상호작용이 많고, API는 단순하다. 백엔드를 분리할 복잡도가 없다.
- PWA·Service Worker·Web Push가 같은 오리진에서 자연스럽게 묶인다.

**포기한 것**: Python 생태계(데이터 처리 라이브러리). 이 제품에는 쓸 일이 없다고 판단.

## ADR-002. RDB를 쓰지 않는다

**결정**: PostgreSQL/SQLite 등 관계형 DB를 두지 않는다. JSON 문서를 그대로 저장한다.

**근거**
- 단일 사용자다. 동시성 제어도, 트랜잭션 격리도 필요 없다.
- 데이터가 자연스럽게 **문서 구조**다(하루 = 엔트리 배열 + 요약). 조인할 대상이 없다.
- 스키마 마이그레이션 비용이 사라진다. 이 프로젝트는 혼자 오래 굴릴 물건이라 이게 크다.
- 사람이 직접 읽고 고칠 수 있다. 최악의 경우 텍스트 에디터가 복구 도구가 된다.

**포기한 것**: 복잡한 집계 쿼리. 월 단위 통계 정도는 메모리에서 계산하면 충분하다.

**재검토 조건**: 전문 검색이 체감될 만큼 느려지면 SQLite FTS를 **인덱스로만** 추가한다(정본은 그대로 파일).

## ADR-003. 월 1파일 + 인덱스 파일

**결정**: 저장 단위를 하루가 아니라 **한 달**로 하고, 달력 렌더 전용 `index.json`을 따로 둔다.

**근거**: 원격이 정본이면(ADR-004) **API 요청 수가 곧 응답 속도**다.

| 파일 단위 | 월 달력 렌더 | 쓰기 1회 전송량 | 판정 |
|---|---|---|---|
| 하루 1파일 | 30회 fetch ≈ 10초 | 2KB | ❌ |
| **월 1파일 + 인덱스** | **1회** | 60KB | ✅ |
| 연 1파일 | 1회 | 700KB | ❌ |

월 파일은 1년이 지나도 60KB 수준이라 전송 비용이 무시 가능하다. 인덱스는 달력이 월 파일 없이 렌더되게 해 요청을 한 번 더 줄인다.

**포기한 것**: git diff의 가독성(하루 1파일이면 diff가 깔끔했다). 요청 수가 더 중요하다고 판단.

## ADR-004. 원격(GitHub)이 정본, 로컬에 기록을 보관하지 않는다

**결정**: 홈서버 디스크에 과거 기록을 두지 않는다. 모든 읽기·쓰기가 네트워크를 탄다.

**결정 주체**: 사용자. 아래 반대 의견을 제시했고, 사용자가 재확인하여 확정했다.

**검토 과정에서 제기된 반대 근거** (기록 목적으로 남김)
1. 용량 이득이 거의 없다. 10년치가 10MB 수준이고 서버 여유는 4GB다(0.25%).
2. 모든 쓰기가 네트워크에 묶인다. 200–800ms 지연, 실패 시 유실 위험.
3. GitHub 계정 하나가 단일 장애점이 된다(토큰 만료·계정 잠김·API 장애).
4. 사본이 사실상 1벌이 되어 "백업"의 정의가 깨진다.

**확정된 선택과 그에 따른 완화 설계**

| 리스크 | 완화 |
|---|---|
| 요청 수 폭증 | 월 1파일 + 인덱스 파일 (ADR-003). 달력 1 fetch |
| 쓰기 지연 | 낙관적 UI — 메모리 즉시 반영 후 백그라운드 동기화 |
| 네트워크 단절 중 쓰기 유실 | **로컬 쓰기 큐** (ADR-006). 지수 백오프 재시도 |
| 원격 장애 중 조회 불가 | 메모리 캐시 범위는 stale로 계속 제공 + 저하 배너 |
| 커밋 폭주 | 10초 디바운스로 변경분을 1커밋에 묶음 |
| 사본 1벌 | 월 1회 `snapshots/` 경로에 tar.gz 2차 사본 |
| 동시 수정 충돌 | blob `sha` 낙관적 동시성, 409 시 재읽기 후 병합 재시도 |

**얻은 것**: 모든 쓰기가 곧 커밋이라 **버전 이력이 공짜로 생긴다.** 별도 주간 백업 잡이 불필요해졌고, "특정 시점으로 복원"이 자연스럽게 가능해졌다.

**재검토 조건**: 네트워크 저하로 입력 경험이 나빠지거나 동기화 실패가 반복되면, 로컬에 **읽기 전용 미러**를 두는 절충안(쓰기는 그대로 원격 우선)을 검토한다.

## ADR-005. Redis를 쓰지 않는다. 캐시는 프로세스 메모리

**결정**: 캐시 계층으로 Redis를 두지 않고 Node 프로세스 안의 LRU Map을 쓴다.

**근거**
- 캐시 대상 전량이 수 MB다. Redis 데몬 자체(RSS 10–30MB)가 **캐시할 데이터보다 무겁다.**
- Node 프로세스가 이미 메모리를 갖고 있다. 같은 데이터를 프로세스 간 통신으로 한 번 더 들고 있을 이유가 없다.
- 인스턴스가 1개다. 프로세스 간 캐시 공유라는 Redis의 본래 가치가 발생하지 않는다.
- 프로세스가 하나 줄면 운영·장애 표면이 그만큼 줄어든다.

**포기한 것**: 재시작 후 캐시 워밍. 첫 요청이 원격 1회 fetch로 느려질 뿐이라 수용 가능하다.

**재검토 조건**: 앱을 다중 인스턴스로 띄울 일이 생기면 그때 도입한다.

## ADR-006. 로컬 쓰기 큐 (미동기화분 한정)

**결정**: 아직 원격에 반영되지 않은 변경분만 담는 append-only 파일(`queue/pending.jsonl`)을 둔다.

**근거**
- ADR-004에서 로컬 보관을 없앴지만, 이것까지 없애면 **네트워크 단절 중 입력한 기록이 조용히 사라진다.** 사용자가 적었다고 믿는 기록이 없는 상태는 이 제품에서 가장 나쁜 실패다.
- 과거 기록 보관이 아니다. 원격 반영 성공 즉시 파일을 비운다. 평상시 0바이트, 최악(일주일 단절)에도 15KB 수준이다.
- 컨테이너 볼륨 1개로 끝난다. 이 볼륨을 통째로 날려도 미동기화분만 잃고 과거 기록은 원격에 그대로 있다.

**불변식**: *큐가 비어 있다 == 모든 변경이 원격에 반영되었다.* 이게 깨지지 않는 한 유실이 없다.

## ADR-007. PWA + Web Push

**결정**: 별도 데스크톱 클라이언트를 만들지 않고 PWA로 OS 알림을 띄운다.

**근거**
- 회사 PC에 실행파일 설치가 자유롭지 않다는 전제. 브라우저만으로 완결되어야 한다.
- 알림 클릭 → 입력 폼 직행이라는 핵심 동선이 Service Worker로 그대로 구현된다.
- 트레이 앱을 만들면 Windows 배포·업데이트·서명이라는 별개의 프로젝트가 생긴다.

**알려진 제약**: iOS Safari는 홈 화면에 추가한 PWA에서만 푸시를 지원한다. 설정 화면에 안내를 넣는다.

**재검토 조건**: 푸시 신뢰도가 실사용에서 부족하면 트레이 앱을 **추가 클라이언트로** 붙인다(서버 구조는 그대로).

## ADR-008. 요약은 Claude API, 키가 없으면 수동 폴백

**결정**: `claude-opus-5`로 요약 초안을 생성하고 사용자가 수정한다. 키가 없으면 수동 작성 UI로 폴백한다.

**근거**
- 요약은 이 제품의 부가가치이지 핵심 저장 기능이 아니다. **외부 의존이 기록 기능을 죽이면 안 된다.**
- `generatedBy` / `editedAt`으로 AI 초안과 사람 손길을 구분해 보관한다. 2단계 이력서 자동 작성에서 **사람이 고친 문장을 더 신뢰할 근거**가 된다.
- 비용은 무시 가능하다(일간 요약 1건 ≈ $0.013, 월 $0.5 미만).

## ADR-009. 서버에서 빌드하지 않는다

**결정**: 이미지를 외부(개발 머신 또는 GitHub Actions)에서 빌드해 레지스트리에 올리고, 홈서버는 pull만 한다.

**근거**
- 홈서버 여유 디스크 4GB에서 **실제 위협은 데이터(10MB)가 아니라 빌드 중 node_modules + .next 캐시(500MB–1GB)다.**
- standalone 출력 + alpine 베이스로 최종 이미지를 200MB 이하로 묶는다.
- 재배포가 `docker compose pull && up -d`로 끝나고 롤백은 태그 교체다.

## ADR-010. 데이터 커밋을 프로필 잔디에서 제외 (전용 author 이메일)

**결정**: 데이터 레포(`*-db`) 커밋의 author/committer 를 **계정에 등록되지 않은 이메일**로 지정한다(기본 `career-log@users.noreply.invalid`, `STORE_COMMIT_EMAIL`로 변경 가능).

**근거**
- 모든 기록 편집이 곧 커밋이라(ADR-004의 덤), 데이터 전용 private 레포에 커밋이 쌓인다. 그 자체는 무해하지만, **GitHub 프로필의 contribution graph(잔디)에 찍혀 실제 코드 작업을 한 것처럼 보이는 게** 사용자에게 부담스러웠다.
- GitHub 잔디는 **커밋 author 이메일이 그 계정에 등록된 이메일일 때만** 집계한다. 등록되지 않은 이메일로 커밋하면 어느 계정에도 귀속되지 않아 잔디에 찍히지 않는다.
- 이 방법은 저장 백엔드(git)를 유지하므로 **버전관리·시점 복원이 공짜로 남고 이전 비용이 0**이다. (대안으로 Google Drive/Notion 이전을 검토했으나, 각각 OAuth 복잡도·데이터모델 재작성/정본 이원화 비용이 커서 기각.)

**한계**: 이 설정 이전에 이미 만들어진 커밋은 계정 이메일로 author 돼 있어 잔디에 남는다. 완전히 지우려면 데이터 레포 히스토리를 1회 재작성(author 이메일 치환)하거나 레포를 재생성해야 한다. 신규 커밋부터는 자동으로 제외된다.

**재검토 조건**: 그래도 git 자체가 싫어지면 Google Drive 어댑터로 교체(저장 계층 경계는 `github.read/write` 계약 하나라 교체 가능). Notion 은 파일 저장소가 아니라 데이터 모델 재작성이 필요해 권하지 않는다.

## ADR-011. 검색은 서버 인메모리 MiniSearch + n-gram (전체 기간)

**결정**: 검색을 **별도 검색엔진·RDB 없이** Next 서버 프로세스 안의 **MiniSearch** 인메모리 인덱스로 구현한다. 한국어 부분일치를 위해 **통단어 + 2글자 n-gram** 토크나이저를 색인·질의에 동일 적용한다. 인덱스는 `store.getAllEntries()`(인덱스가 아는 월 전체를 캐시로 읽음)로부터 lazy 빌드하고, 데이터 시그니처가 같으면 프로세스 전역에서 재사용한다.

**근거**
- 데이터가 작다(1인·수년 = 수백 KB~수 MB). 전용 검색엔진/RDB는 ADR-002·005 위반이자 과잉. 전체를 메모리에 올려 검색하는 게 정석이다.
- 기간 제한(2-tier) 방식은 "기간 없이 전체 검색"이 어렵다. 인메모리 전량 색인이면 전체 기간이 가볍고 랭킹·증분이 좋다.
- MiniSearch는 소형(의존성 1개, ~6KB)·순수 JS·서버에서 동작. Fuse(스캔·랭킹 약함)·Lunr(영어 스테밍·불변 인덱스)·FlexSearch(API 투박)·Orama(과함) 대비 균형이 좋다.
- 한국어는 단어 경계가 약해 단어 토큰화만으론 "결제"→"결제API"가 안 걸린다. 2gram이 부분일치를 흉내 낸다.

**한계·대안**
- career-db 에는 **기록만** 둔다(ADR-004). 검색 인덱스는 메모리에만, 저장하지 않는다(ADR-006 유지). 원격이 죽으면 검색만 저하되고 기록은 영향 없다(제약 6).
- 최초 검색 때 월 전체를 1회 읽는다(이후 캐시). 쓰기 후에는 시그니처가 바뀌어 다음 검색에 재빌드한다.
- 1글자 질의는 n-gram 특성상 약하다(최소 2글자 권장).

**재검토 조건**: 데이터가 커져 메모리 전량 색인이 부담되거나 태그/본문 필터를 전체 기간에 더 빨리 돌려야 하면, `index.json`에 태그·토큰을 넣어(색인 전용, 저장 계층 변경) 2단계의 기술스택 누적 통계와 함께 재설계한다.

## ADR-012. 커리어 메타데이터는 career-db 안 `meta/` 폴더, 성과는 수동 추출·큐레이션

**결정**: 2단계 "성과 모음"의 데이터를 데이터 레포(career-db) 안 **`meta/achievements.json`**에 둔다. 기록(`journal/`)과 폴더로 분리한다. 성과 추출은 **수동 버튼**으로만 돌리고(자동 배치 아님), AI가 뽑은 후보 중 사용자가 고른 것만 저장한다. 성과 항목은 제목(필수) + 선택 상세(문제→접근→결과+기술+주제+근거날짜) 구조다.

**근거**
- career-db 는 "업무 기록"이 정본인데(ADR-004), 성과 모음은 기록이 아니라 **기록에서 뽑은 메타데이터**다. 별도 레포를 하나 더 두는 운영 비용보다, 같은 레포 안에서 `meta/` 로 **폴더 분리**하는 편이 단순하다(설정·요약도 이미 같은 레포에 있다).
- 사용자의 실제 작업은 스택이 좁아(C# 서버) "기술스택 인벤토리"가 가치가 낮다. 대신 **무엇을·어떻게·어떤 효과**(문제→접근→결과)가 이력서/포트폴리오 근거가 된다. 그래서 성과를 그 구조로 잡았다(경력기술서·포트폴리오 실물 분석 기반).
- **상세는 선택**이다. 모든 성과에 문제/접근/결과가 있지 않으므로, 뽑아낼 수 있을 때만 채우고 아니면 한 줄로 둔다.
- 추출을 **수동**으로 한 이유: 자동 배치는 노이즈가 쌓이고 비용·예측성이 나쁘다. 사용자가 범위를 정해 뽑고 고르는 큐레이션이 품질을 지킨다.
- 추출 프롬프트의 **system 은 설정에서 커스텀**, **JSON 출력 형식은 코드 고정**(앱이 파싱하므로 사용자가 깨면 안 됨).

**한계·재검토 조건**: `meta/` 가 커지거나 커리어 데이터가 기록과 독립적으로 백업·공유돼야 하면 별도 레포로 분리한다. 경력기술서·포트폴리오로의 **내보내기**는 3단계에서 ⭐ 성과를 회사·테마별로 조립해 구현한다(지금은 적립까지만).

## ADR-013. 공개 Showcase: `/showcase`만 로그인 없이, SSR 전용·화이트리스트

**결정**: 2-3 공개 포트폴리오(Showcase)를 연다. 인증 미들웨어에서 **`/showcase` 와 그 하위 경로만** 화이트리스트에 넣어 로그인 없이 접근 가능하게 하고, 나머지(기록·요약·설정·모든 `/api/*`)는 그대로 세션을 요구한다. 공개 페이지는 **서버 렌더(SSR) 전용**으로, 서버에서 `meta/`(profile·projects·achievements)만 읽어 렌더한다. **별도 공개 JSON API(`/api/public/*`)는 만들지 않는다.** 성과는 **기본 공개**, `hidden`인 것만 제외하며, `star`는 홈 대표로, `projectId`로 프로젝트에 묶인다.

**근거**
- 공개 표면을 최소화하는 게 가장 안전하다. 페이지가 SSR이라 서버에서 큐레이트 데이터만 읽어 HTML로 내보내면 되고, 그러면 **공개 HTTP API를 하나도 열 필요가 없다**(엔드포인트가 적을수록 실수로 비공개 데이터를 노출할 틈이 적다). 제약 #6·#7(비밀값은 서버에만, 클라이언트 번들에 토큰 금지)과도 맞는다.
- 공개 경로는 `/showcase` 접두사로만 판정한다(`=== "/showcase"` 또는 `startsWith("/showcase/")`). `/showcaseXYZ` 같은 유사 경로는 열리지 않는다.
- Showcase 데이터 로더(`loadShowcase`)는 **journal·summaries·settings를 절대 읽지 않는다.** achievements는 `hidden` 제외. 근거 날짜는 연도 라벨로만 보이고 일지로 가는 링크는 없다.
- 저장 타입(Achievement·Project)을 그대로 넘기지 않고 **허용 필드만 담은 공개 DTO**(`showcase/types.ts`)로 바꿔 렌더한다. 클라이언트 컴포넌트 props 는 RSC 페이로드로 브라우저에 그대로 실리므로, 저장 타입에 필드가 늘어도(생성 시각·작성 주체·정확한 근거 날짜 등) 공개로 새지 않게 하기 위함이다.
- 공개 경로 판정은 `src/lib/public-paths.ts` 한 곳(미들웨어·헤더 공용)에서만 하고, 공개/비공개 경로 목록을 테스트로 고정한다.
- 공개/비공개를 **기본 공개 + 숨김 옵션**으로 한 이유: 포트폴리오라 대부분 공개가 맞고, 개별 공개 토글은 켜는 걸 잊기 쉽다. 숨기고 싶은 것만 opt-out 하는 게 단순하다.

**한계·재검토 조건**: 외부에서 JSON으로 소비할 일이 생기면 그때 **읽기 전용 공개 API**를 명시적으로 추가한다(그때도 `hidden`/비공개 필드 필터를 서버에서 강제). 일부 성과를 숨기는 수준을 넘어 **섹션 단위 비공개**가 필요해지면 `profile`에 공개 플래그를 둔다. 채용공고 맞춤·테마 맵 등은 3단계.

## ADR-014. 보안 강화: 레이트리밋 키·세션 무효화·CSRF 2차선·보안 헤더

**배경(점검에서 찾은 문제)**
- **로그인 레이트리밋 우회**: nginx 는 `X-Forwarded-For` 에 실제 IP 를 **덧붙이는데**(`$proxy_add_x_forwarded_for`) 앱은 그 **첫 값**을 IP 로 썼다. 첫 값은 클라이언트가 정하므로, 요청마다 바꾸면 IP별 5회 제한이 사라져 무차별 대입이 가능했다.
- **세션을 끊을 방법이 없음**: 토큰은 서명만 검증하는 무상태 JWT 이고 슬라이딩 갱신이라, 탈취된 쿠키는 쓰는 한 영원히 유효했다. 비밀번호를 바꿔도 기존 세션이 살아 있었다.
- **오픈 리다이렉트**: 로그인 후 `next` 검사가 `//` 만 막아, `/\evil.com`(브라우저가 `//evil.com` 으로 해석)으로 외부 이동이 가능했다.
- **보안 헤더 없음**: 클릭재킹(iframe 삽입)·MIME 스니핑·HSTS·CSP 방어가 없었다.
- **CSRF 방어가 한 겹**: SameSite=Lax 쿠키에만 의존했다.

**결정**
- 레이트리밋 키는 nginx 가 **덮어쓰는 `X-Real-IP`** 를 쓴다(없으면 XFF 의 마지막 값). 앱은 `127.0.0.1` 에만 바인딩돼 nginx 를 거치지 않고는 닿지 않으므로 이 헤더는 신뢰할 수 있다. IP별(1분 5회)에 더해 **전체 1분 30회** 백스톱을 둬 IP 를 바꿔 가며 하는 분산 대입도 막는다. 비밀번호는 256자로 길이를 제한한다.
- 세션 토큰에 **비밀번호 해시 지문(`pv`)**과 **최초 인증 시각(`at`)**을 넣는다. 비밀번호를 바꾸면 이전 세션이 전부 무효(= 전체 로그아웃 수단). 갱신해도 `at` 은 유지되어 **최대 90일**이 지나면 다시 로그인해야 한다. 기존 토큰(지문 없음)은 무효 — 배포 직후 한 번 다시 로그인한다.
- 로그인 후 리다이렉트는 `safeNextPath` 로 **같은 출처 경로만** 허용한다.
- 미들웨어에서 **Origin 이 우리 호스트가 아닌 상태 변경 요청(POST/PUT/PATCH/DELETE)은 403**. Origin 이 없는 요청(서버 스크립트)은 쿠키 인증에 맡긴다(백필 스크립트 호환).
- 응답 헤더: `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, 그리고 운영에서만 `HSTS`(서브도메인 제외)와 `CSP`(`'self'` 기반, `frame-ancestors 'none'`, `object-src 'none'`).
- 판정 로직은 순수 함수(`request-security.ts`)로 두고 테스트로 고정한다(IP 위조, CSRF, 리다이렉트 우회, 레이트리밋, 세션 무효화).

**한계·재검토 조건**
- CSP 는 Next 인라인 스크립트 때문에 `script-src 'unsafe-inline'` 이다. nonce 기반 strict CSP 는 모든 페이지를 동적 렌더로 바꿔야 해서 보류한다. 사용자 입력을 HTML 로 렌더하는 기능(마크다운 등)을 넣게 되면 그때 nonce CSP 로 올린다.
- 레이트리밋은 프로세스 메모리라 재시작 시 초기화된다. 인스턴스가 늘거나(ADR-005 재검토) 공격이 실제로 관측되면 nginx `limit_req` 로 앞단에서도 막는다.
- 인증된 API 의 오류 응답에 원격 오류 메시지가 실린다(비밀값은 없음). 다중 사용자가 되면 일반화한다.

## ADR-015. 프로젝트 사진은 career-db `meta/media/`에, 기간은 월 단위 구조화, 기존 글은 자르지 않는다

**결정**
- **사진 저장**: 프로젝트 사진(프로젝트당 최대 10장)을 데이터 레포 `meta/media/<projectId>/<photoId>.<ext>` 에 둔다. 외부 저장소(S3 등)는 쓰지 않는다.
- **업로드 전 처리**: 브라우저에서 긴 변 1600px·WebP(안 되면 JPEG)로 다시 인코딩한다 — 장당 수백 KB, 900KB 상한(nginx 기본 1MB 안쪽). 캔버스로 다시 그려 **EXIF(촬영 위치 GPS 등)를 지운다**.
- **서버 검증**: 형식은 업로드된 **바이트 시그니처**로만 판별(webp·jpg·png). 파일명·Content-Type 은 믿지 않고, SVG 처럼 스크립트를 품을 수 있는 형식은 받지 않는다.
- **공개 응답**: `/showcase/media/<projectId>/<photoId>`(공개 경로, ADR-013). 프로젝트 목록에 **등록된 사진만** 내보내 임의의 레포 파일을 읽을 수 없게 한다. photoId 는 내용이 바뀌면 새로 발급(불변)하므로 1년 `immutable` 캐시 + 프로세스 메모리 LRU(32MB).
- **기간**: 경력·프로젝트 기간은 자유 글자 대신 **월 단위 "YYYY-MM"** 시작/종료(경력: 재직 중, 프로젝트: 진행 중 + 시작·종료 코멘트). 목록은 날짜로 최신순 정렬. 예전 자유 글자는 읽을 때 옮기고, 옮기지 못하면 원문을 남겨 화면에서 수정을 안내한다.
- **기존 글은 자르지 않는다**: 입력 한도(한마디·비고 500자 등)는 입력 화면에만 적용한다. 서버는 저장된 글을 읽을 때 절대 자르지 않고, 저장 시에도 남용 방지 상한(4000자)으로만 막는다.

**근거**
- 정본은 원격 레포(ADR-004), 로컬 무보관(ADR-006), 프로세스·외부 의존 최소(ADR-005, 제약 6)와 맞는다. 외부 저장소는 새 비밀값·장애 지점·비용을 늘린다. 사진도 같은 레포라 **시점 복원**에 함께 되돌아간다.
- 장당 수백 KB × 10장 × 프로젝트 수라 레포 크기 영향이 작다(수~수십 MB). Contents API 쓰기 한도(100MB)와 무관.
- 월 단위는 이력서 관례이고, 기억이 흐린 과거 날짜에 가짜 정밀도를 만들지 않는다. 구조화해야 최신순 정렬·재직 기간·총 경력(겹침 제외) 계산이 된다.
- 한도를 서버에서 "읽을 때" 적용했더니 실제로 기존 한마디가 잘려 보였다(배포 전 실데이터 확인에서 발견). 한도는 바뀔 수 있는 UI 정책이고, 이미 쓴 글을 지우는 건 되돌릴 수 없는 데이터 손실이라 분리한다.

**한계·재검토 조건**
- 지운 사진도 git 이력에는 남는다(레포 크기). 사진이 수백 장 규모가 되거나 레포가 수백 MB 를 넘으면 Git LFS 또는 외부 저장소로 옮긴다.
- `/api/export`(JSON 내보내기)에는 사진이 빠진다. 사진까지 2차 사본이 필요해지면 내보내기에 포함한다.
- 업로드 상한이 nginx 기본값에 묶여 있다. 원본 화질 보관이 필요해지면 `client_max_body_size` 를 올리고 상한을 함께 조정한다.
